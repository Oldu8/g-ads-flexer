# Roadmap

Порядок работ, принятые решения и открытые вопросы. Как устроена система —
[`PLATFORM_ARCHITECTURE.md`](./PLATFORM_ARCHITECTURE.md). Что именно
строится — OpenSpec-изменения в
[`../openspec/changes/`](../openspec/changes/). История решений — в
`mcp-server/TRACKER.md` и в git.

Обновлено 2026-09-25: планирование завершено (итерации 1–3), дальше идёт
реализация.

## 1. Решения

- **D1 — поверхность инструментов раньше бэкенда.** Хостед-энтрипоинт
  подключает готовый профиль, а не хардкод-список.
- **D2 — агент видит профиль, а не все 366 инструментов.** `read_only`
  вычисляется из `manager`, руками не пишется.
- **D3 — доступ к инструментам задаётся колонкой.**
  `ad_accounts.tool_profile` хранит имя профиля, содержимое профиля — YAML
  в репозитории.
- **D4 — записи уже в пилоте.**
- **D5 — очередь изменений только в Postgres.** JSON-хранилище удаляется.
- **D6 — подтверждение изменений в чате.** Дашборда с дифом в MVP нет.
- **D7 — никакой привязки к аккаунту в коде.** Аккаунт появляется только
  через Google-вход и discovery, одинаково для оператора и для клиента.
- **D8 — одна очередь для всех записей.** Google проверяет изменение через
  `validate_only`, применяет только `apply_pending_change`. Флага
  `confirm` нет.
- **D9 — одна БД, клиенты разделены по строкам.** `ad_account_id` берётся
  из токена, а не из аргументов.
- **D10 — все миграции у `web/`, на Drizzle.**
- **D11 — один Supabase-проект, схемы `app` и `app_dev`.** Отдельные роли и
  ключи шифрования; dev-роль не видит prod.
- **D12 — минимальный кабинет делается раньше хостед-бэкенда.**
- **D13 — профиль `manager`:** ядро + ассеты-расширения + таргетинг и
  корректировки ставок + аудитории. 77 инструментов, из них 44 записи.
- **D14 — потолки.** 500 строк на ответ; `tools/list` ≤ 25k токенов для
  `manager` и ≤ 10k для `read_only`; 1 500 операций в сутки и 60 в минуту
  на аккаунт; стоп проекта на 90% от 15 000.
- **D15 — refresh-токены шифруются AES-256-GCM ключом приложения.**
- **D16 — оба приложения на Railway.**
- **D17 — сценарий агентства (2026-09-25).** Маркетолог входит
  Google-аккаунтом с доступом к рабочему MCC, выбирает нужные рекламные
  кабинеты и на **каждый** получает отдельный MCP (токен) и отдельную
  таблицу fixes-лога. У пользователя может быть сколько угодно кабинетов.
  Оплата и управление ими сейчас не проектируются.

Технические решения, принятые при написании спеки (обратимые, обоснования
в OpenSpec):

- Точка контроля — gRPC-интерсептор: закрепление аккаунта, `validate_only`
  при постановке в очередь, учёт квоты.
- `customer_id` скрыт из схем инструментов, его подставляет сервер.
- `context` аккаунта передаётся через инструмент `account_context`.
- Одна MCP-ссылка `/mcp`, аккаунт определяется токеном; локальный
  `main.py` работает по токену из кабинета.
- Таблицы названы `ad_accounts` и `google_connections` (второе — это
  таблица Auth.js).
- Новый аккаунт получает `read_only`; изменения включаются тумблером.
- `google-ads` 33.0.0 (API v25.2); developer token удалён отовсюду (2026-09-25).

## 2. Фазы

```
Фаза 0 (оператор) ── проверка доступа ──┐
Фаза A  mcp-server ─────────────────────┼──► Фаза C ──► Фаза D ──► Фаза E
Фаза B  web + БД  ◄── после проверки ───┘
```

Фаза A от посылки о доступе не зависит, её можно начинать сразу. Фазы B и
C строятся на том, что одного Google-входа достаточно, поэтому начинаются
только после проверки из Фазы 0.

### Фаза 0 — Google (оператор)

**0.1 Проверить, что Google-входа действительно достаточно.** Займёт около
получаса.

1. *Консоль, 5 минут.* Проект `178951272716`:
   - [Google Ads API → Overview](https://console.cloud.google.com/google/ads-apis/overview?project=178951272716):
     уровень доступа. ✅ **Basic** — подтверждено 2026-09-25.
   - *APIs & Services → OAuth consent screen:* статус публикации (Testing
     или In production), тип пользователей, список test users.
   - *Google Auth Platform → Clients:* клиент `boo-ua-mcp-desktop` (тип
     Desktop, ID `178951272716-9ruurq3oqt3b4e7lit46iatked5up8tt…`). Консоль
     больше не показывает и не отдаёт существующий секрет: взять его из
     старого `.env` или нажать *Add secret* (старый при этом продолжает
     работать, выданные refresh-токены привязаны к клиенту, а не к секрету).
2. ✅ *Прогон от своего имени* — пройден 2026-09-25, все проверки PASS
   (MCC `9587322149`, 6 активных аккаунтов, запись через `validate_only`).
   Команда (войти аккаунтом, у которого есть доступ к MCC):
   `cd mcp-server && uv run scripts/verify_google_access.py --client-id 178951272716-9ruurq3oqt3b4e7lit46iatked5up8tt.apps.googleusercontent.com --label operator --write-env .env`.
   Скрипт спросит секрет скрытым вводом. Флаг `--write-env` заодно
   восстанавливает локальный `.env`, и
   MCP-сервер из `.mcp.json` снова стартует.
3. *Прогон от второго Google-аккаунта — решающий тест, сценарий
   агентства (D17).* Нужен Google-аккаунт, у которого никогда не было
   developer token. В Google Ads **на уровне своего MCC** (Admin → Access
   and security) выдать ему доступ Standard: так он окажется в положении
   маркетолога, пришедшего со своим рабочим MCC. Если экран согласия в
   режиме Testing, добавить его в test users. Затем:
   `uv run scripts/verify_google_access.py --client-id 178951272716-9ruurq3oqt3b4e7lit46iatked5up8tt.apps.googleusercontent.com --label second-identity`.
4. *Консоль после прогонов:* в метриках Google Ads API проекта видны эти
   запросы, значит квота списывается с нашего проекта.

Что проверяет скрипт: C0 — OAuth-клиент принадлежит проекту `178951272716`;
C1 — запросы проходят вообще без заголовка `developer-token`; C2 — мусорный
заголовок игнорируется; C3 — аккаунт с прямым доступом читается без MCC;
C4 — аккаунты под менеджером доступны через `login-customer-id`; C5 —
запись разрешена (проверка через `validate_only`, ничего не создаётся);
C6 — работает путь через SDK, которым пользуется наш сервер. Отчёт
сохраняется в `mcp-server/tmp/`.

Как читать результат:

- **Всё PASS в обоих прогонах** — посылка подтверждена. Отметить в
  `TRACKER.md` с request-id и снять пометку «не проверено» в
  `PLATFORM_ARCHITECTURE.md`.
- **C1–C3 FAIL с ошибкой авторизации или уровня доступа** — проект не
  получил уровень при миграции. Смотреть консоль (шаг 1), до выяснения B и
  C не начинать.
- **C5 FAIL при PASS C1–C4** — чтение работает, запись нет (например,
  Explorer или Test). Это меняет D4 (записи в пилоте) и заявку на уровень.
- **Второй аккаунт не может пройти согласие** — его нет в test users, или
  приложение не проверено. Это вопрос Фазы 0.2, а не API.

**0.2 Разблокировать внешних пользователей.** Домен, homepage + privacy +
terms, brand verification проекта, подача `adwords` на верификацию. До её
прохождения пилот идёт на test users, и их refresh-токены живут 7 дней.

### Фаза A — поверхность инструментов → `agent-surface-profiles`

Реестр и аннотации инструментов, профили и middleware, envelope ответов,
подсказки в ошибках, golden-снимки и бюджеты, исправление `page_size` и
строки лицензии. 14 задач. Только `mcp-server/`.

### Фаза B — БД и минимальный кабинет → `platform-db-and-cabinet`

Next.js + Drizzle, все таблицы, роли и схемы, Auth.js с `adwords`,
шифрование токенов, discovery, экран аккаунта. 13 задач.

### Фаза C — хостед-бэкенд и записи → `hosted-multitenant-writes`

Креды на запрос, интерсептор, верификатор токенов, `hosted_main.py`,
очередь записей, квота, локальный режим через токен, удаление старых
механизмов (`remote_main.py`, JSON-хранилища, реестр алиасов). 20 задач.

### Фаза D — пилот

Сначала аккаунты оператора, подключённые через кабинет, затем 5–10
внешних пользователей. Метрика: недельная активность через 3 недели и
заявленная готовность платить.

### Фаза E — после пилота

Standard access (демо-аккаунт, описание guarded writes и fixes log как
механизма контроля изменений, RMF для профиля `manager`, подача при
среднем за 7 дней ≥ 7 500 операций), биллинг, дашборд изменений, ротация
токенов, RLS.

## 3. Открытые вопросы

- **Принимают ли MCP-клиенты пилотных пользователей статический
  bearer-токен?** Claude Desktop / claude.ai и ChatGPT могут требовать
  OAuth. Проверить до пилота: от этого зависит, как кабинет выдаёт доступ.
- **Название продукта и домен.** Блокирует 0.2, но не код.
- **Таблица fixes-лога на кабинет: создаёт её платформа или пользователь
  вставляет свою?** Сейчас в спеке второе (поле `fixes_sheet_id` и
  расшаривание на сервисный аккаунт). Решить до Фазы B.
- **Формулировка заявки на Standard** при профиле `manager` вместо узкого
  whitelist полей (Фаза E).

## 4. Бэклог (не запланировано)

- Справочная документация как MCP-ресурсы вместо длинных docstring.
- Энамы прямо в схемах инструментов вместо ошибок в рантайме.
- Хелперы экранирования для GAQL.
- Eval выбора инструментов с базовыми замерами токенов.
- Skill, поставляемый вместе с сервером.
- Переименовать заикающиеся имена `search_search_*` (изменит
  golden-снимки).
- Кэш результатов GAQL на аккаунт для экономии квоты.

`google-ads-mcp` от Google, Apache-2.0). Если переносить оттуда код
дословно, нужно сохранить лицензионный заголовок и добавить запись в
`mcp-server/NOTICE.md`. Это допустимо, потому что наш репозиторий под
AGPL-3.0.
